# Local coordinator: rounds
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies; this file holds how a batch's rounds are given, handed off, briefed and recorded.

## Paths, not content
- Dev's task: the path of the batch's `spec-<batch>.md`, the batch's base ref and the project rule files that apply (see "Briefs carry the project's conventions"). Never name tests or smoke sections for Dev: Dev runs only the linter and the type check or build; every test run is the Tester's.
- The Tester's brief: the same spec path plus the state ("Briefed rounds" below). You never read, copy, write or rewrite a spec: a spec change is the Planner's (`decide` or `replan`).
- Reports: each worker writes its full report to a file (`<its scratchDir>/reports/<task_id>.md`, its `--report-path`) and its `worker_done` body holds the status line, a short summary and that path. Open a report file only when you act on it: a finding, a question, a Dev decision about something the spec should have settled, or a `close`. Pass report paths, not their text, to the next role.
- When the project's tests need browsers (Playwright and the like), a Deployer task installs them once per worktree, before the first Tester round ("Install the project's test browsers"); record it in `conventions.md`, and every Tester brief says they are installed.

## The routine handoff
After Dev's `worker_done` on a batch, when there is nothing in it to act on (no question, no decision to route), run from the worktree `~/.orca-roles/bin/handoff.sh <batch> --to <tester handle> --run <run_id> --spec <spec path> --report <Dev's report path>`, adding `--tree <path>` for a batch in a pair tree and `--note "<text>"` for state the report does not hold (a ruling, a user decision). It records the checkpoint, writes the Tester brief, appends the ledger line, creates the Tester task and dispatches it; its last line is `handoff: <batch> round <k> task <task_id> brief <path>`. Exit 0: the round is dispatched. Any other exit: nothing was dispatched, and it says what it recorded; tell the user in one line and do that round by hand as "Briefed rounds" says. Step in yourself only on a REJECTED, a question or a decision.

## Fixes
All open findings of a batch go to Dev in one fix task (the path of the report that holds them and the findings routed to Dev), then one Tester round. All the fixes a `close` decides go to Dev in one task and to the Tester in one round, each given the path of the Planner's `close` report and the findings routed to it.

## The set's ledger
Keep one ledger per set, `ledger.md` in your scratchDir: the set's base commit, the plan's path, and one line per event, each naming its batch: the checkpoint refs, the report paths and their verdicts, the findings open and closed, what was not audited. `handoff.sh` writes the line of each routine handoff; after a Tester report add `- <UTC time> <batch> Tester round <k>: <verdict>; report <path>; checkpoint <the ref checkpoint.sh just printed>`, so the Code-Reviewer knows on which ref each report's green runs ran. The ledger is the source of every brief, and you check it before closing a batch and before proposing the set's commits: every finding is closed or accepted by the user. The project conventions live apart, in `conventions.md` in your scratchDir, kept across sets; every Planner task names both paths. At the set's commits, after `checkpoint.sh --clear-all`, move `ledger.md` and `changes-log.md` to `archive/<UTC date>-<short HEAD>/` in your scratchDir; the next set starts new ones. A ledger that still holds earlier sets (an older kit): at the next set, move its "Project conventions" section to `conventions.md` and the rest to `archive/ledger-before-sets.md`.

## Briefed rounds
Workers cannot read other tasks' specs or results (`dispatch-show` does not return them), so every Tester task and every Code-Reviewer task carries a self-contained brief with two parts, written as paths wherever a file holds the content. *The task*: the path of the batch's spec (its steps' goals, contracts, criteria with their pass/fail examples, threat model and rejection threshold); for the Code-Reviewer, the plan's path and every spec path of the set. *The state*: the files changed, the path of Dev's report (what Dev did and decided) and any other context relevant to the batch; for the Code-Reviewer, also, for every batch of the set, the paths of the Tester reports (what the Tester did and found, its "Green runs on the delivered tree" and its self-mutants) with the checkpoint ref the ledger records for each, every green run of its own earlier reviews with its ref, and the "Full suite" line of the set's ledger (`not run in this set` until there is one). From the second round on, it also says what earlier rounds already verified, the findings still open and the "not audited" items carried forward (the ledger's lines and the reports they name), so nobody redoes them. The first brief to each role carries the whole batch's diff (the first hint line `checkpoint.sh` prints: from the previous batch's last checkpoint, or from HEAD for the first batch of the set), and every Tester brief names the batch's base ref (the start of that diff: that checkpoint's ref, or HEAD) for its base check; a later brief to a role carries `git diff <ref of the checkpoint its previous brief pointed to> <latest ref>`, so it covers everything Dev and the Tester changed since that role last looked, test-only rounds included, and how far the worker goes is its call. `handoff.sh` writes the routine Tester brief this way; write the others yourself. The brief passes information only: it never tells the Tester or the Code-Reviewer what to test, mutate or look at, or where the risks are; their prompts and judgment decide that within their own parameters. The green runs and the "Full suite" line are state too: the Code-Reviewer decides with `checkpoint.sh --same` whether each run still stands, and whether its review ends with the full suite. The sections and tests the change touches are part of the state (the spec names them for the Tester), not an instruction on what to test, mutate or look at.
