# Local coordinator: parallel batches
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies; this file changes only how many batches run at once and in which tree.

## Which batches run, and where
- Each batch of the plan has a `Depends on:` line naming the earlier batches it depends on (`none` when it has none). In an older plan whose `Depends on:` lines are on steps, a batch depends on every batch that holds a step one of its steps depends on. A batch is **ready** when every batch it depends on is closed and, if it ran in a pair tree, integrated.
- At the set's start, and each time a batch closes or is integrated, look at the ready batches that have not started. Exactly one ready and no batch open: run it in the worktree, as local-coordinator.md says. Otherwise run each ready batch, in plan order, in its own **pair tree**: a detached git worktree outside the worktree, with its own Dev and Tester. A batch whose Dev or Tester `launch.sh --add` refuses waits for the next close; tell the user in one line, quoting the REFUSED line.
- The batches run one at a time in the worktree, as before, when a batch has no `Depends on:` line (and its steps have none either), or a line names a batch or step that does not exist (send the Planner a `decide` task), or Dev or the Tester cannot run instances, or `pair-tree.sh create` refuses because of the repository (initialised submodules, or a linked dependency that points back into the worktree; tell the user in one line, quoting its message).
- A Researcher brief that measures time, load, memory or capacity never runs while a pair tree has a task in flight.
- A task for the worktree (Dev, the Tester, an integration run) goes only to a tab that runs in the worktree: one with no line in `orca-roles.trees` (in the worktree's git dir). While any pair tree is open, open one with `~/.orca-roles/bin/launch.sh --add <id>` (no `--tree`), never `--open`: the role's own tab may be working in a pair tree. When that `--add` is refused, wait for a close; never give the task to a tab of a pair tree.

## A batch in a pair tree
1. **Base ref.** In the worktree, `~/.orca-roles/bin/checkpoint.sh <batch>-start <n>` (n = 1, and one more for each redo of the batch): the ref it prints is the batch's base ref.
2. **Tree.** `~/.orca-roles/bin/pair-tree.sh create <batch> <base ref>`, without asking the user; its last output line is the tree's path. Pair trees are made and removed only with `pair-tree.sh`, never with `git worktree` or `orca worktree create`.
3. **Pair.** `~/.orca-roles/bin/launch.sh --add dev --tree <path>`, then `~/.orca-roles/bin/launch.sh --add tester --tree <path>`, without asking the user; dispatch to each once "Roles reopened" gives its handle. If the Tester's `--add` is refused after the Dev's was opened, close that Dev (`close-role.sh <dev instance>`) and `pair-tree.sh remove --force <batch>`: the batch waits for the next close. Record in the batch's ledger the tree's path, the base ref and both instance ids.
4. **Flow.** The batch runs Phase 2 as in the worktree, with three differences: every `checkpoint.sh` of the batch runs in its tree, `(cd <path> && ~/.orca-roles/bin/checkpoint.sh <batch> <n>)`; the base ref of the Dev task and of every Tester brief is the batch's base ref; `round.sh`, when you record rounds, runs in the tree with `ORCA_ROLES_STATE` and `ORCA_ROLES_CONFIG` set to the worktree's `orca-roles.env` and `orca-roles.config.json` (in its git dir).
5. **Integrate**, after the batch's ACCEPTED and its closing checkpoint, while no code task and no E2E-Tester task is in flight in the worktree and no other integration is running: `~/.orca-roles/bin/pair-tree.sh integrate <batch> <closing ref>`.
   - Exit 0: the batch's work is in the worktree, unstaged. In the worktree, record `~/.orca-roles/bin/checkpoint.sh integ <n>` (n counts the set's integrations), then run `~/.orca-roles/bin/checkpoint.sh --same <closing ref>`: `same` means the batch's green runs still stand there; `differs` means the worktree also holds other batches' work (see "Integration run").
   - Exit 4 (`conflict <batch>: <patch path>`): nothing was written. Redo the batch on the current worktree: close its pair (point 6, `pair-tree.sh remove --force <batch>`), take points 1-3 again, and give its Dev a fix task: apply the saved patch (that path) to the new tree and resolve the conflicts git reported, keeping each step's spec; then a Tester round with the batch's full brief (the context is new), then integrate again.
6. **Close the pair** after the integration: `~/.orca-roles/bin/canary.sh --run <run_id>`, `~/.orca-roles/bin/close-role.sh <dev instance> <tester instance>` and `~/.orca-roles/bin/pair-tree.sh remove <batch>`, without asking. Its checkpoint refs stay: the ledger's green runs point to them.
7. **After the integration.** Phase 2 points 5-7 of the batch's steps (the E2E test, `local-coordinator-e2e.md`; the performance validation; the Deployer's guide) run in the worktree after its integration; a fix they need is a code task in the worktree. The batch closes (point 8) only after them, and only then counts as closed for the batches that depend on it.

## Integration run
When `checkpoint.sh --same` says `differs` after an integration, then before any batch that depends on the integrated ones starts and before the set audit, give a Tester that runs in the worktree (see "Which batches run, and where") an integration run: a brief that starts with `Integration run`, the latest `integ` ref, and every "Green runs on the delivered tree" command the ledgers record for the batches integrated since the last integration run. Record its green runs against that ref like any other. A red run is a REJECTED round: route its findings as Phase 2 item 4 says, with Dev in the worktree.

## Set close
- The set audit starts when every batch is closed and integrated and `~/.orca-roles/bin/pair-tree.sh list` shows no tree `open` or `integrated`.
- After the set's commits, with `checkpoint.sh --clear-all`, run `~/.orca-roles/bin/pair-tree.sh clear`.
- After a restart, `pair-tree.sh list` names the trees still open; their Dev and Tester tabs reopen in them (launch.sh keeps each tab's tree).
