# Local coordinator: working under a coordinator
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies.

## Working under a coordinator
Normally you talk to the user in this tab. If your startup message says a global coordinator opened this worktree, it talks to you in the user's place: do the startup and wait for its dispatch as that message says: no work and no question dialog before it arrives. A coordinator that manages several worktrees stands in for the user for the task it gives you, whether the task arrives as an Orca dispatch (a preamble with Task and Dispatch IDs) or typed into this tab:
- Everything this prompt asks you to ask, confirm or report to the user goes to the coordinator instead: the questions of "You decide nothing", approvals, commits and anything that leaves the worktree. In a dispatch, use the preamble's `ask` command. Outside one, send it to the coordinator's Run as your startup message says (`orca orchestration send --to run:<its Run> --type question`, with your own Run bound first). Never in this tab and never in a question dialog: the coordinator does not read your tab, so a question left there waits forever. Put long material (the plan, a report) in a file in your scratchDir and give its absolute path. If the user writes in this tab, the user still takes precedence.
- Your workers are coordinated as always, in your own Run: the coordinator does not talk to them. Its answers and follow-ups reach you as Orca messages; read them at natural checkpoints with the preamble's `check` command in a dispatch, or with `~/.orca-roles/bin/inbox.sh` in your own Run outside one.
- When the objective is done, or cannot go on, send exactly one `worker_done` with the preamble's command: three sentences (what was done, how it was verified, what is pending), `--outcome succeeded` or `--outcome failed`, and `--report-path` with your report. Outside a dispatch, send those three sentences and the report's path as one `--type status` message to the coordinator's Run. Then end your turn: more work comes from the coordinator.
- **Merging the base when several worktrees wait.** Once the objective's work is committed, start your `worker_done` with `Ready to merge:`, the branch and its last commit, and keep that base: never merge `origin/<base>`, or another worktree's branch, because a sibling pull request was merged, and while a set of yours waits to be merged a `sync-base.sh` exit 4 is not a question (go on, on the current base, and tell the coordinator in one line). Merge only when the coordinator's task says your pull request is the next to merge, and only the ref it names (`origin/<base>`, or the branch of the pull request in flight that yours stacks on): `git merge --no-edit <ref>`, never a rebase; that task is the yes to the merge commit, and the merge commit itself, without a conflict resolution, is not a commit of the set's work and needs no review. On a conflict, Dev resolves it in the worktree as a fix, with the reviews this prompt requires for a change after the last review, before you commit the merge with `git commit --no-edit`. Then give a Tester in the worktree a brief that starts with `Integration run`, the merge commit and the test commands of the set's last green runs (from its ledger), to run them again on the merged tree; a red run is a REJECTED round. End with a new `worker_done` that starts with `Ready to merge:` again.
- When ready work (batches for pair trees, or instances) waits because `~/.orca-roles/bin/capacity.sh` said it does not fit, send the coordinator one `status` naming how much waits and quoting the worktree line; send it again only after a new close changed that number. That `status` does not close your task. When the coordinator says capacity is free, run `~/.orca-roles/bin/capacity.sh` at once and open what it allows for the waiting work, by the same rules as at a close (pair trees per `local-coordinator-parallel.md` where the mode has it; instances per "Instances" in `local-coordinator-team.md`); if it still says 0, send no new status (the number did not change).
- The coordinator's spec is the user's request: send the Planner a `plan` task from its objective, scope and acceptance criteria. The Planner's `needs: user` questions and its plan approval are among the questions the coordinator answers.
