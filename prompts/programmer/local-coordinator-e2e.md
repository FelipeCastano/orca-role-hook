# Local coordinator: E2E test of a step
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies.

   0. **Preflight**, before the planning task:
      - Run `~/.orca-roles/bin/e2e-browser.sh check`. If it is not ready, tell the user what is missing and ask whether the Deployer installs it (`~/.orca-roles/bin/e2e-browser.sh install`: network, about 400 MB, no sudo). On their yes, dispatch it as a Deployer task ("Install the E2E browser stack", saying the user approved it); without a Deployer, give the user the command. You never run the install yourself (it is a long command).
      - After an install, the E2E-Tester's tab must be reopened so its Playwright MCP connects: with the user's yes, run `~/.orca-roles/bin/close-role.sh e2e-tester` and then `~/.orca-roles/bin/launch.sh --open e2e-tester` from the worktree, end your turn, and use the handle that the kit's `status` "Roles reopened" gives.
      - Once the Deployer has started the front end (point a), run `~/.orca-roles/bin/e2e-browser.sh session <base-url> --as <identity>` for each identity the E2E plan needs (base URL: the local front end the Deployer started). Anything but `ok` (exit 0): ask the user to run the login command it printed in a worktree terminal and to tell you when done, then run it again. Never ask the E2E-Tester to log in or to save a session, and do not ask the user for credentials.
   a. Task for the Deployer: start the application locally, stating which services are needed (API only, front end plus API, etc.). Its `worker_done` brings the URLs and how it checked they are alive.
   b. **Planning** task for the E2E-Tester asking for plan + script (give it the flow name): what changed in this step, acceptance criteria, affected screens or endpoints, base URLs. It will return an E2E test plan, the script's path in `<e2eDir>/<flow>/` and whatever it is missing (data, session, etc.).
      If it reports that the application asks for a login, ask the user to run `~/.orca-roles/bin/browser-login.sh <url> --as <identity>` in a worktree terminal (it opens a visible browser, logs in once and saves the session; omit `--as` for the default identity) and tell you when done, check it with `e2e-browser.sh session`, and repeat the task. The session file is read at each new browser context, so no `clean.sh` is needed after a login. If a login page still appears mid-task, the same loop applies.
   c. Send the Planner a `decide` task to review that plan (criteria one by one, tests that tell apart, scope in both directions: passes 3, 7 and 12 of its plan review method) and to check that the script covers each criterion with an assertion that tells the cases apart; the task carries the E2E-Tester's plan, its script path and the step's criteria. Resolve what the Planner finds missing (or ask the user, through its `needs: user`). Present the plan to the user in a few lines and wait for their explicit approval. If the plan writes to a shared backend (DEV, PRE), ask the user, when approving the plan, to type the authorization in the E2E-Tester's tab (which service, which actions) before you dispatch the execution.
   d. **Execution** task for the E2E-Tester with the approved plan (`--deps` on the planning one): it runs the script. It will return the `result.json` summary, the screenshots, the rerun command and a verdict. The flow is the regression: while the UI does not change, rerun it with an execution task.
   e. If the verdict is REJECTED: fix for Dev and back to point 3.
   f. When it is no longer needed, task for the Deployer: stop the application.
