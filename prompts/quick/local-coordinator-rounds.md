# Local coordinator: rounds
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies; this file holds how a batch's rounds are given, handed off, briefed and recorded.

## Paths, not content
- Dev's task: the path of the batch's `spec-<batch>.md`, the batch's base ref and the project rule files that apply (see "Briefs carry the project's conventions" in local-coordinator.md). Never name tests or smoke sections for Dev: Dev runs only the linter and the type check or build; every test run is the Tester's.
- Before creating each Dev task, run `~/.orca-roles/bin/oracle.sh --lint <spec path>` from the worktree: exit 0, create and dispatch the task; exit 1, do not: fix the spec yourself with the lint's output and lint it again, and if it still fails tell the user and wait; exit 2, tell the user in one line and do not dispatch; exit 3 (no python3 >= 3.8), tell the user in one line and dispatch without the lint.
- The Tester's brief: the same spec path plus the state ("Briefed rounds" below). A spec change after the plan is yours, made with the user as "Changes outside the plan" in local-coordinator.md says.
- Reports: each worker writes its full report to a file (`<its scratchDir>/reports/<task_id>.md`, its `--report-path`) and its `worker_done` body names it. Open a report file only when you act on it: a finding, a question, a Dev decision the spec should have settled, or a spec change of your own. Pass report paths, not their text, to the next role; findings routed to a fix are still copied exactly as their reporter wrote them.

## The routine handoff
After Dev's `worker_done` on a batch, when there is nothing in it to act on (no question, no decision to route), run from the worktree `~/.orca-roles/bin/handoff.sh <batch> --to <tester handle> --run <run_id> --spec <spec path> --report <Dev's report path>`, adding `--note "<text>"` for state the report does not hold (a user decision, a `Decision (local coordinator):` line). It records the checkpoint, writes the Tester brief, appends the ledger line, creates the Tester task and dispatches it. Exit 0: the round is dispatched. Any other exit: nothing was dispatched, and it says what it recorded; tell the user in one line and do that round by hand as "Briefed rounds" says. Step in yourself only on a REJECTED, a question or a decision.

## Fixes
All open findings of a batch go to Dev in one fix task (the path of the report that holds them and the findings routed to Dev, copied exactly as their reporter wrote them), then one Tester round.

## The set's ledger
Keep one ledger per set, `ledger.md` in your scratchDir (the file `handoff.sh` appends to): the set's base commit, the plan's path, and one line per event, each naming its batch: the checkpoint refs, the report paths and their verdicts, the findings open and closed, and every `User decision:` and `Decision (local coordinator):` line. After a Tester report add `- <UTC time> <batch> Tester round <k>: <verdict>; report <path>; checkpoint <ref>`. The project conventions live apart in `conventions.md` in your scratchDir, kept across sets. At the set's commits, after `checkpoint.sh --clear-all`, move `ledger.md` to `archive/<UTC date>-<short HEAD>/` in your scratchDir. A scratchDir that still holds a ledger file per batch (an older kit): leave those files as they are and start `ledger.md`.

## Briefed rounds
Workers cannot read other tasks' specs or results (`dispatch-show` does not return them), so every Tester task that `handoff.sh` does not write carries a self-contained brief with two parts, written as paths wherever a file holds the content. *The task*: the path of the batch's spec (its steps' goals, contracts, criteria with their pass/fail examples, threat model and rejection threshold). *The state*: the files changed, the path of Dev's report (what Dev did and its decisions) and any other context relevant to the batch. From the second round on, it also says what earlier rounds already verified and the findings still open (the ledger's lines and the reports they name), so nobody redoes them. The first brief to each role carries the whole batch's diff (`git diff <the batch's base ref> <latest ref>`), and every Tester brief names the batch's base ref for its base check; a later brief carries `git diff <ref of the checkpoint its previous brief pointed to> <latest ref>`, so it covers everything Dev and the Tester changed since that role last looked, test-only rounds included, and how far the worker goes is its call. `handoff.sh` writes the routine Tester brief this way; write the others yourself. The brief passes information only: it never tells the Tester what to test, mutate or look at; its prompt and judgment settle that within its parameters. The sections and tests the change touches are part of the state (the spec names them for the Tester), not an instruction on what to test, mutate or look at.
