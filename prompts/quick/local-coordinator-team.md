# Local coordinator: roles opened on demand and instances
Read on demand from local-coordinator.md (same folder), which names the moment to read it. Everything in local-coordinator.md still applies.

## Opening a role
Before a role's first task (for one opened per task, before each of its tasks; for one opened per batch, before its first task of each batch) run `~/.orca-roles/bin/launch.sh --open <id>` from the worktree without asking the user, end your turn, and dispatch to it only once the kit's `status` "Roles reopened" gives its handle (if launch.sh prints "All roles are already open.", no message comes: dispatch at once with the handle it printed, unless it also printed that the previous kickoff is still running: then wait for the message that kickoff sends, or, if none comes before your next turn, run `~/.orca-roles/bin/launch.sh --open <id>` again; if it fails, tell the user what it printed and dispatch nothing to that role).

## Closing a role
- **Per task.** After the `worker_done` of a role opened per task, once no question or follow-up of that task is pending, close it with `~/.orca-roles/bin/close-role.sh <id>` without asking, unless the user asked to keep it open.
- **Per batch.** A role opened per batch keeps its tab through every round of the batch. When the batch closes (its ACCEPTED verdicts and its closing checkpoint), close each role opened per batch that worked in it with `~/.orca-roles/bin/close-role.sh <id>` without asking, unless the user asked to keep it open; such a role is closed, not cleaned, at the batch close. In a mode with a set audit, the corrections after it count as one batch, which closes when the Code-Reviewer's corrections review is ACCEPTED.
- Run `~/.orca-roles/bin/canary.sh --run <run_id>` before each close, as "Report marker" says.

## Instances
A role your startup message lists as able to run several instances can have more than one tab at once. `~/.orca-roles/bin/launch.sh --add <id>` opens one more, without asking the user: the role's own tab when it has none, else the instance `<id>-<n>` with the lowest free number, titled `<Title> <n>`. It prints `Instance: <instance id> (<title>) opening.`; then end your turn and dispatch to it once "Roles reopened" gives its handle (the line `<ROLE>_<n>=<handle>`, for example `RESEARCHER_2=...`), as for `--open`. An instance has its own handle, task, scratch folder and report, and is closed like its role (per task: after its report) with `~/.orca-roles/bin/close-role.sh <instance id>`. If launch.sh exits 3 with a line starting `REFUSED:`, nothing was opened: the role's or the team's maximum, or the machine's load or free memory, said no. Do not retry at once; give the task to the first tab of that role that reports, and tell the user in one line, quoting the REFUSED line. A `Note:` line says a hardware check could not run; go on. Use `--add` only for what "Researchers in parallel" allows, and for what `local-coordinator-parallel.md` and `local-coordinator-e2e.md` allow where your mode has them.

## Researchers in parallel
When two or more Researcher briefs are ready at once (a Planner's `needs: research:` items, or briefs you write yourself) and they are independent, run them in parallel: none needs another's answer, each names its own output files, and none measures time, load, memory or capacity (such a brief runs alone, with no other Researcher running, because parallel runs distort each other's measurements). Only while no code task is in flight ("One step at a time" still applies). For each brief, in turn: `launch.sh --add researcher`, then its own Researcher task with that brief only. Handle each report as it arrives and close that instance; once every brief of the group has reported, pass all the results on together (to the Planner's next task, or to your own planning). Briefs that are not independent run one after another on one Researcher.
